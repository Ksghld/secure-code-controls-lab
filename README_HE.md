# Secure Code Controls Lab - מדריך מעשי

המעבדה סינתטית בלבד. אין פריסה לענן, Build, סודות או סריקת חולשות אמיתית.
שני המאגרים מפרידים בין קוד היישום לבין מדיניות וסורק מרכזיים.

## הרצה מקומית
מתיקיית האב של שני המאגרים:
```text
secure-code-controls-lab\.venv\Scripts\python.exe -m pytest -q secure-code-controls-lab/tests central-security-workflows-lab/tests
```
קובץ requirements.txt מגדיר תלויות לבדיקות בלבד. הסורק המרכזי אינו מתקין תלויות מהיישום.

## שלבי העבודה
1. מנהל מורשה יוצר את המאגרים ומאשר את הרשאות תהליך הפרסום הקיים.
2. מזהה המאגר הציבורי מקושר לרישום המרכזי, וכל אי-התאמה נכשלת באופן סגור.
3. יוצרים ענף Feature ומבצעים Commit מקומי:
```bash
git switch -c codex/clean-pr
git add src/demo.txt
git commit -m "Update synthetic sample"
```
4. שולחים את הענף ופותחים PR באמצעות העזרים המאושרים בלבד. ממשק העזרים תלוי בסביבה; אין להמציא נתיב הזדהות.
5. בודקים ב-Actions שהניטור וה-PR Gate רצו דרך ה-Workflow המרכזי ובוחנים את קובצי ה-Evidence.
6. מוסיפים ל-src/demo.txt את SIMULATED_CRITICAL_SCA. בניטור הממצא מדווח; באכיפה הוא מכשיל.
7. דוחפים Commit נוסף לאותו PR ובודקים שנוצרה בדיקה חדשה עבור ה-SHA הרלוונטי.
8. מתקנים את הממצא וממתינים לאישור ולמיזוג אנושי בלבד.
9. אחרי המיזוג מאמתים שבדיקת השחרור נבדקה על ה-SHA שהגיע בפועל ל-main.

## Ruleset
מנהל המאגר מגדיר Settings -> Rules -> Rulesets עבור main בלבד.
יש לדרוש PR, את שם ה-Check המדויק מתוך Checks API ואת המקור GitHub Actions,
ולמנוע Force Push ומחיקה. אין להניח ששם ה-Job הקורא הוא שם ה-Check המלא.
דרישת ביקורת עצמאית מחייבת זהות מורשית נוספת; ללא שתי זהויות אין הוכחת ארבע עיניים.
ניסוי דחיפה ישירה ל-main מתבצע רק במסגרת בדיקת מנהל נפרדת; הסוכן אינו מורשה לבצעו.

## SHA וגבולות אמון
PR Head SHA הוא קצה ענף התורם. GitHub validation SHA ב-PR עשוי להיות Test-Merge.
לאחר מיזוג יש SHA נפרד שאותו בודקים מחדש. אין להשתמש בבדיקה ירוקה ישנה כהוכחה ל-SHA אחר.
הסורק נטען מהמאגר המרכזי לפי SHA קבוע; קובצי היישום הם טקסט לא מהימן בלבד.
עם זאת, תורם יכול לשנות את ה-Caller. מקור GitHub Actions אינו הוכחה לשלמות ה-Workflow.
אישור עצמאי כבר הודגם ב-PR מספר 6. קובצי CODEOWNERS וכללי הבעלות נמצאים בשינוי נפרד לביקורת; אין לטעון שהם נאכפים לפני מיזוג והפעלה בפועל.
בייצור נדרשת אכיפה בלתי תלויה בבעל הקוד.

## ראיות
TEST_RESULTS.md מתעד רק בדיקות שבוצעו. P0_REMOTE_VALIDATION.md הוא יומן הניסויים המרוחקים.
כבר אומתו ניטור, שער PR מרכזי, ביקורת עצמאית ובדיקת SHA לאחר מיזוג. היומן מבדיל בין תוצאות שנצפו לבין בדיקות שעדיין ממתינות. התאמת Code-to-Cloud היא סימולציה ולא Provenance חתום.
